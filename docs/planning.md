## 1. サービス概要

Coffee Compass は、コーヒーにこだわりのあるカフェを、自家焙煎・スペシャルティコーヒーなどの店舗特徴タグから探し、その店で実際に飲まれたログから焙煎度・味わいの傾向を確認できるサービスです。

スペシャルティコーヒーや自家焙煎のカフェに興味を持ち始めたものの、味わいの違いや自分の好みをまだうまく言語化できない人が、自分に合いそうなお店や一杯を見つけやすくすることを目指しています。

飲んだログを記録することで、自分の好みを振り返り、次のカフェ選びや一杯選びに活かせます。

---

## 2. 企画の背景

### 2-1. きっかけとなった体験

Coffee Compass のアイデアは、カフェを探す中で感じた
**「コーヒーにこだわりのあるカフェを見つけにくい」**
という経験から生まれました。

コーヒーに興味を持ち始め、休日にカフェ巡りをするようになった頃、Google Maps や口コミサイトを見ても、その店がどのようなコーヒーにこだわっているのか分かりにくいと感じました。
場所・営業時間・雰囲気・写真・評価などは簡単に確認できますが、どのカフェがコーヒーにこだわっているのかを判断しづらく、店選びに迷うことがありました。

また、コーヒーにこだわりのあるカフェを見つけても、複数の豆やメニューの中から自分の好みに合う一杯を選ぶのは簡単ではありませんでした。
産地・焙煎度・精製方法・テイストノートなどの情報があっても、それが自分の好みとどう結びつくのかが分かりにくかったためです。

この体験から、まずは **コーヒーにこだわりのあるカフェを見つけやすくすること**、そのうえで **自分の好みに合いそうな一杯を選びやすくすること**、さらに **飲んだ体験を記録して次の選択に活かすこと** を支援したいと考えました。

### 2-2. なぜそれが気になったのか

コーヒーの楽しさは、詳しい人だけのものではなく、良いお店や自分に合う一杯と出会うことで、誰でも少しずつ広げていけるものだと考えています。

自分自身も最初は、口コミや雰囲気を頼りにカフェを探していました。
しかし、飲む経験が増えるにつれて、自分なりの好みを意識するようになりました。

一方で、最初から自分の好みを言語化し、メニュー選びに活かすのは難しいと感じました。
そのため、まずはカフェ情報や飲んだログを通じて、自分の好みに合いそうなカフェや一杯を見つけやすくしたいと考えました。

## 3. 解決したい課題

### 3-1. 表に見えている困りごと

Google Maps や口コミサイトでは、カフェの場所・営業時間・雰囲気・評価は分かります。
しかし、その店がどのようなコーヒーに強いのか、自分の好みに合う一杯が飲めるのかは判断しにくいと感じました。

また、コーヒーを飲んだあとも、そのコーヒーの印象を記録できないと、自分の好きな味の傾向を振り返りにくいことも課題でした。

### 3-2. 本当に解決したい課題

- なぜ？
  コーヒーにこだわりのあるカフェかどうか判断できないと、口コミや雰囲気だけで店を選ぶことになるため。
- なぜ？
  口コミや雰囲気だけでは、その店で自分の好みに合うコーヒーが飲めるか分かりにくいため。
- なぜ？
  自分の好みや飲んだ体験を整理できないと、次のカフェ選びや一杯選びに活かしにくいため。

→ 本当に解決したい課題：
**コーヒーに興味を持ち始めた人が、味わいの違いや自分の好みをうまく言語化できず、カフェ選びや一杯選びに活かしにくいこと**

既存の地図アプリや口コミサイトでは、場所や評価をもとにカフェを探すことはできます。
一方で、焙煎度・味わい・提供スタイルなど、コーヒー視点で比較するには情報が分散しており、初心者には判断が難しいと感じました。

Coffee Compass では、専門的なコーヒー情報を、初心者でも選びやすいタグや記録項目として整理しています。

## 4. 想定ユーザー

### 4-1. 想定しているユーザー

| 観点 | 設定 | 理由 |
|---|---|---|
| 年齢 | 20代〜30代 | 休日や仕事帰りにカフェを利用する機会があり、Google Maps や Instagram を使って外出先でカフェを探す場面が多いため。スペシャルティコーヒーや自家焙煎のカフェに興味を持ち始める年代だと考えています |
| 生活・状況 | 休日や仕事帰りに、スペシャルティコーヒーや自家焙煎のカフェを探す人 | こだわりのある店に興味はあるものの、浅煎り・深煎り・味わい・提供スタイルなどの情報を、自分の好みや一杯選びに結びつけるのが難しいため |
| 環境 | Google Maps、Instagram、口コミサイトでカフェを探している | 既存サービスでは場所・営業時間・雰囲気・評価は確認しやすい一方で、どのような焙煎度・味わい・提供スタイルのコーヒーが飲めるのかは比較しにくいため |

### 4-2. 自分とユーザーの距離

**過去の自分**を想定ユーザーにしています。

コーヒーに興味を持ち始めた頃、どのカフェがコーヒーにこだわっているのか、どの豆やメニューが自分に合うのかを判断するのが難しかったためです。
そのため、想定ユーザーは「スペシャルティコーヒーや自家焙煎のカフェに興味を持ち始めたが、選び方にまだ自信がない人」としています。

### 4-3. 使ってくれそうな人・思い出す場面

**まず最初に使ってくれそうな人**

- スペシャルティコーヒーや自家焙煎のカフェに興味を持ち始めた人
- Google Maps や SNS だけでは、自分好みの店か判断しづらい人
- カフェで複数の豆やメニューを見たとき、一杯選びに迷う人
- 飲んだコーヒーや行ったカフェを記録したい人

**このアプリを思い出す場面**

- 外出先でカフェを探すとき
- 初めて行くエリアで、コーヒーにこだわりのあるカフェを探したいとき
- カフェでどのコーヒーを選べばよいか迷ったとき
- 以前飲んだコーヒーや行ったカフェを思い出したいとき

**今、代わりに使われているもの**

Google Maps / Instagram / 口コミサイト / メモアプリ / 写真フォルダ

**それを置き換えてまで使う理由**

- 自家焙煎・スペシャルティコーヒーなどの店舗特徴タグから、コーヒー視点でカフェを探せる
- 店舗ごとの飲んだログから、実際にどんなコーヒーが飲まれているのかを確認できる
- 飲んだログを残すことで、自分の好みを振り返り、次回以降のカフェ選びや一杯選びに活かせる

### 4-4. 利用の流れ（実装後の実際の導線）

```text
カフェ検索・閲覧はアカウント登録なしで利用できる
  ↓
エリア（都道府県）・特徴タグ・カフェ名からカフェを探す
  ↓
カフェ詳細ページで店舗情報と「みんなのログ」「味わいの傾向」を見る
  ↓
記録を残したくなったらアカウント登録（メール または Google アカウント）
  ↓
飲んだコーヒーをログとして記録する（自宅で淹れた一杯も記録できる）
  ↓
マイページで自分のログを振り返る
```

## 5. 競合との違い

### 5-1. 調査した類似サービス

| サービス | できること |
|---|---|
| [Good Coffee](https://goodcoffee.me/coffeeshop/) | 厳選されたコーヒーショップをエリア別に探せる。こだわりのある店舗の情報を確認できる |
| [Google Maps](https://www.google.com/maps) | 現在地やエリアからカフェを検索できる。営業時間、写真、口コミ、評価、経路を確認できる |
| [食べログ](https://tabelog.com/) | カフェや飲食店をエリア・ジャンル・口コミ・評価で探せる。写真や口コミから雰囲気や人気度を確認できる |

### 5-2. それでも作りたかった理由

既存サービスでもカフェを探すことはできますが、「コーヒー視点で自分に合う店や一杯を選ぶ」体験には、まだ不足している情報があると感じました。

Google Maps は、現在地周辺のカフェを探したり、営業時間・写真・口コミ・経路を確認したりするには便利です。
一方で、その店が浅煎りに強いのか、深煎りに強いのか、ハンドドリップを提供しているのか、どのような味わいのコーヒーが飲まれているのかは分かりにくいです。

食べログは、飲食店としての評価や口コミを確認するには便利ですが、コーヒーの味わい・豆の特徴・抽出方法を軸に比較する用途には向いていないと感じました。

Good Coffee は、コーヒーにこだわりのある店舗を知るうえで非常に参考になるサービスです。
一方で Coffee Compass では、店舗を探すだけでなく、その店舗で実際に飲まれたログを確認し、自分自身も記録を残すことで、次回以降の選択に活かせる点を重視しています。

### 5-3. 差別化を一文で

**店舗ごとの飲んだログをもとに、カフェ探しだけでなく店内での一杯選びまで支援すること。**

## 9. 当初計画から変えた判断

実装を進める中で、企画時点の想定から変更した点です。

### 9-1. 味わいタグを「大項目 / 小項目」の2階層にした

企画時点では、味わいタグを単純なリストとして考えていました。
しかし実際に記録してみると、**記録したい粒度と、集計して意味が出る粒度が違う**ことが分かりました。

- 記録するときは細かく残したい（例：「ベリー」ではなく「ストロベリー」）
- 集計して傾向を見るときは大きくまとめたい（細かすぎると票が割れて傾向が出ない）

そこで `tags` に `parent_id` を持たせて2階層にし、集計時は `Tag#aggregation_target`（親があれば親、なければ自分）を通すことで、記録の粒度と集計の粒度を分離しました。
現在は大項目12種類・小項目48種類を用意しています。

また、コーヒーに詳しくないユーザー向けの選択UIでは、通常の表示順とは別に `beginner_display_order` を持たせ、選びやすい順で並べています。

### 9-2. 味わいの強さの入力を「ドラッグ並び替え」から「選択順」に変えた

企画時点では、タグを選んだあとに**ドラッグで優先順位を並び替える**UIを想定していました。

実装では、**選択した順序をそのまま「強く感じた順」として保存**する方式にしています。
選んだタグにはチップと順番のバッジが表示され、順序を変えたいときは「×」で外して選び直します。

スマートフォンでの利用を前提にしているため、ドラッグ操作を持ち込まずに順序を表現できる形を選びました。
順序は中間テーブル `drink_log_taste_tags` の `position` に保持しています。

### 9-3. 「みんなのログの傾向」を重み付け集計にした

企画時点では、傾向表示は「よく使われている味わいタグ」＝単純な出現回数を想定していました。

9-2 で選択順を保持できるようになったため、**先に選ばれたタグほど高いスコアを与える**重み付け集計（`DrinkLog#weighted_taste_tag_scores`）に変更しています。
これにより「たまたま多く選ばれている味わい」ではなく「その店で強く感じられている味わい」が上位に出るようにしました。

### 9-4. 認証に Google ログインを追加した

企画時点では Devise によるメール認証のみを想定していました。

記録を始めるまでのハードルを下げたかったため、OmniAuth による Google アカウントでのログインを追加しています。
あわせて、Google 連携ユーザーはアプリ側からメールアドレスを変更できないよう制限しています。

### 9-5. カフェに紐づかない「自宅記録」を許容した

企画時点では、飲んだログは必ずカフェに紐づく前提でした。

しかし、自宅で淹れた一杯も同じように記録して振り返りたいと考え、`drink_logs.brewed_at_home` を追加しました。
`cafe_id` は `optional` にしたうえで、自宅記録でないときだけカフェを必須にするバリデーションを置き、「カフェのログ」と「自宅のログ」を1つのモデルで扱っています。

自宅記録はマイページには表示されますが、店舗ページの「みんなのログ」には出ません。

### 9-6. 二重投稿の防止をDBレベルで担保した

企画時点では想定していなかった問題です。

通信のリトライやブラウザバックからの再送信で、同じログが2件保存される可能性がありました。
そこで投稿フォームに `idempotency_key` を持たせ、`user_id` との複合ユニークインデックスで**DBレベルで重複を防ぐ**構成にしています。
フロント側（Stimulus）の二重送信防止と併用しています。

### 9-7. CIを最初から自動化した

企画時点では「MVPではCI自動化までは行わず、手動実行で主要機能の動作確認を行う」と書いていました。

実際には開発開始と同時に GitHub Actions を設定し、Pull Request ごとに **RSpec / RuboCop / Brakeman** を自動実行しています。
毎回手元で3つのコマンドを流すより確実で、結果的にこちらの方が楽でした。あわせて Dependabot も設定しています。

### 9-8. Rails 7.2 → 8.1

企画時点では Rails 7.2 系を想定していましたが、開発初期（2026-06-12）に 8.1 系へアップデートしています。

## 10. 懸念点は実際どうなったか

### 懸念①：初期データが少ないと価値を感じにくい

**現状：まだ課題として残っています。**

開発用の seed データとして、名古屋・東京のカフェ10店舗（愛知5・東京5）と、焙煎度5種類・店舗特徴10種類・味わいタグ大項目12種類 / 小項目48種類を用意しました。
本番のカフェ情報は管理画面から登録する運用にしていますが、掲載店舗数とログの蓄積は引き続き増やしていく必要があります。

一方で、「探す → 店舗情報を見る → みんなのログを見る → 自分のログを残す」という基本体験自体は、データが少ない状態でも成立することは確認できました。

### 懸念②：ユーザーによるカフェ情報の登録申請が増えると運用負荷が高くなる

**現状：顕在化していません。**

カフェ情報の登録・編集を管理者に限定する方針を維持しているため、承認作業や通報対応は発生していません。
ユーザーによるカフェ登録申請を導入する段階で、承認フロー・通報機能・投稿ステータス管理を検討します。

### 懸念③：簡易診断や好み分析がないと差別化が弱く見える

**現状：一部は補えましたが、本質的には残っています。**

簡易診断・個人の好み分析・レコメンドは未実装のままです。
ただし、9-1 〜 9-3 の味わいタグ設計と店舗ごとの重み付け傾向表示によって、「その店でどんな味わいが感じられているか」は MVP の段階から見られるようにしました。

「自分の好みを自動で分析・可視化する」体験は未着手なので、ここが次の主要テーマになります。

## 11. 技術選定と、その後の変更

### 11-1. 現在の構成

| 分類 | 技術 | 選定理由 |
|---|---|---|
| 言語 | Ruby 3.3 | Rails との相性が良く、記述量が少なく読みやすいため |
| フレームワーク | Rails 8.1 | カフェ・ユーザー・タグ・ログを関連付けて扱うDB中心のWebアプリと相性が良いため。MVCに沿って画面・処理・データを整理しやすい |
| DB | PostgreSQL 16 | 関連データを扱うため。将来のブックマーク・好み分析・レコメンドへの拡張も考慮 |
| 認証 | Devise / OmniAuth (Google) | 登録・ログインを効率よく実装するため。閲覧はゲスト可、記録はログインユーザー限定に切り分け |
| 認可 | Pundit | 投稿者本人・管理者で操作範囲を分けるため。Policy に集約して保守しやすくする |
| 画像 | Active Storage / S3 | ログ写真・アバター・カフェ画像のアップロードと保存 |
| ページング | Kaminari | 一覧の件数が増えたため |
| メール | Resend | パスワード再設定メールなどの本番送信 |
| ビュー | ERB / Hotwire (Turbo・Stimulus) / Tailwind CSS | フロントを分離せず Rails 内で完結させ、実装スピードを優先。少量のJSで済むUI操作は Stimulus で対応 |
| インフラ | Render / Docker / Docker Compose | デプロイをシンプルに保ち、開発環境は再現性を確保するため |
| 品質 | RSpec / RuboCop / Brakeman / GitHub Actions / Dependabot | テスト・スタイル・セキュリティを Pull Request ごとに自動確認 |

### 11-2. 後から追加した技術

| 技術 | 追加した理由 |
|---|---|
| OmniAuth (google-oauth2) | 登録のハードルを下げるため（9-4） |
| Active Storage + aws-sdk-s3 | 写真投稿を MVP 後すぐに実装したため。本番は S3、開発はローカルディスク |
| Kaminari | カフェ・ログの件数が増え、一覧の一括表示が重くなったため |
| Resend | 本番環境でパスワード再設定メールを届ける必要があったため |
| devise-i18n | 認証まわりの文言を含め、表示文言を i18n に統一したため |

### 11-3. チャレンジしたかった点と、その結果

| 当初挙げた点 | 結果 |
|---|---|
| カフェ・タグ・ログ・ユーザーの関連設計 | 味わいタグを親子構造にしたことで、集計軸の設計まで踏み込めた |
| ゲスト利用とログイン後利用の切り分け | `authenticate_user!` のスキップ範囲を明示して整理できた |
| 投稿者本人と管理者で権限を分ける認可設計 | Pundit の Policy に集約し、リクエストスペックでも検証している |
| エリア・タグ・カフェ名を組み合わせた検索 | スコープに切り出し、検索条件UIと候補APIまで実装した |
| スマートフォンで使いやすい検索UI | 検索条件のモーダル化とカフェ名の候補表示を追加した |
| 診断・分析を将来追加しやすい設計 | 味わいタグの集計軸を `aggregation_target` に寄せたことで、集計処理を差し替えやすい形にはできた |
| RSpec / RuboCop / Brakeman による品質確認 | CIで自動化した（9-7） |

### 11-4. 不安だった点の振り返り

| 当初の不安 | 実際 |
|---|---|
| DB設計が複雑になりすぎる可能性 | タグを1テーブルに `category` で集約し、親子構造で拡張する形に落ち着いた |
| 検索条件が増えるとコントローラ・ビューが複雑になる可能性 | 検索条件はモデルのスコープに切り出し、コントローラは組み立てに専念する形にした |
| 診断・分析を最初から入れると MVP が広がりすぎる | 予定通り後回しにし、MVP は約2週間で動く状態にできた |
| 管理者機能を作り込みすぎる可能性 | カフェ・タグの管理と一覧のみに絞り、ログ管理画面は作っていない |

## 12. 今後の展開

Coffee Compass は、カフェ情報を掲載して終わりではなく、ユーザーが飲んだコーヒーのログを蓄積することで、自分の好みを振り返り、次に行きたいカフェや飲みたい一杯を見つけやすくするサービスへ発展させたいと考えています。

### 次に取り組みたいこと

1. **簡易診断** — 質問に答えると、自分に合いそうな味わいの傾向が分かる
2. **個人の好み分析** — 蓄積したログから、自分がよく選ぶ焙煎度・味わいを可視化する
3. **レコメンド** — 過去のログに近い味わいのカフェ・メニューを提案する
4. **地図・現在地検索** — 外出先でカフェを探しやすくする
5. **ブックマーク** — 気になるカフェを後から見返せるようにする

### その先

- ユーザーによるカフェ登録申請と管理者承認フロー、通報機能
- いいね・コメント・フォローなどのコミュニティ機能
- ログ投稿数や訪問店舗数に応じた称号機能
- 店舗アカウントによる豆・抽出方法・季節限定メニューの発信

### 機能以外の工夫

- 地域ごとのカフェ巡り企画
- ユーザーのログをもとにした特集
- コーヒーにこだわりのある店舗を応援できる運営
- 管理者確認済み店舗の表示による情報の信頼性向上
