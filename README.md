# ☕ Coffee Compass

**コーヒー視点でカフェを探し、飲んだ一杯を記録して、自分の好みを振り返る手がかりをつくるサービス。**

🔗 **https://coffeecompass.jp**

---

## 1. Coffee Compass とは

Google Maps や口コミサイトでは、カフェの場所・雰囲気・評価は分かっても、
**「その店がどんなコーヒーにこだわっているのか」「自分の好みに合う一杯が飲めるのか」** は判断しにくいと感じていました。

Coffee Compass は、自家焙煎・スペシャルティコーヒーといった**店舗の特徴タグ**でカフェを探せて、
その店で実際に飲まれたログから**焙煎度・味わいの傾向**を確認できるサービスです。
飲んだ一杯を記録することで、自分の好みを振り返れます。

想定しているのは、スペシャルティコーヒーや自家焙煎のカフェに興味を持ち始めたものの、
味わいの違いや自分の好みをまだうまく言語化できていない人です。

> 企画の背景・課題整理・競合調査・ペルソナ設計などの検討過程は [docs/planning.md](docs/planning.md) にまとめています。

## 2. 主な機能

### ゲスト（ログイン不要）

| 機能 | 説明 |
|---|---|
| カフェ検索 | エリア（都道府県・複数選択可）・特徴タグ・カフェ名を組み合わせて検索 |
| 検索サジェスト | カフェ名の入力途中で候補を表示 |
| カフェ詳細 | 基本情報・営業時間・定休日・公式サイト / Instagram・Google Maps 導線 |
| みんなのログ | その店舗で実際に飲まれたログ一覧 |
| 店舗ごとの味わい傾向 | 投稿ログを集計し、よく選ばれている焙煎度・味わいを表示 |
| ログ詳細 | 公開されているログの詳細を閲覧 |
| 公開プロフィール | 他ユーザーのログ一覧と、記録数・訪問カフェ数を閲覧 |

### ログインユーザー

| 機能 | 説明 |
|---|---|
| アカウント登録 / ログイン | メールアドレス または **Google アカウント**（ログイン状態の保持に対応） |
| 飲んだログの投稿 | メニュー名・焙煎度・味わいタグ・感想メモ・日付・写真 |
| 味わいタグの詳細記録 | 大項目・小項目から、感じた強い順に選択して記録 |
| 自宅記録 | カフェに紐づかない「自宅で淹れた一杯」も記録できる |
| 画像投稿 | ログ写真・アバターをクロップして投稿 |
| ログの編集 | 投稿者本人のみ |
| ログの削除 | 投稿者本人のみ |
| マイページ | 自分のログ一覧・振り返り |
| プロフィール編集 | 表示名・アバター |

### 管理者

| 機能 | 説明 |
|---|---|
| 管理ダッシュボード | カフェ管理・タグ管理への入口 |
| カフェ管理 | 登録・編集・公開状態（下書き / 公開 / 閉店）の切り替え |
| タグ管理 | 焙煎度 / 味わい / 店舗特徴タグの登録・表示順・有効無効の切り替え |

## 3. 使い方の流れ

```text
カフェを探す
  ↓
店舗情報を見る
  ↓
その店舗で飲まれたログや味わいの傾向を見る
  ↓
自分に合いそうな一杯を選ぶ
  ↓
自分も飲んだログを残す
  ↓
マイページで自分のログを振り返る
```

## 5. 設計・実装で工夫した点

### 味わいタグを「大項目 / 小項目」の親子構造で持たせた

`tags` テーブルに `parent_id` を持たせ、味わいタグを2階層で管理しています。

- **記録するときは細かく**（例:「ベリー」「柑橘」）
- **集計するときは大きく**（例: どちらも「フルーティー」として集計）

`Tag#aggregation_target`（親があれば親、なければ自分）を通すことで、
記録の粒度と集計の粒度を分離しました。

コーヒーに詳しくないユーザー向けの選択UIでは、通常の `display_order` とは別に
`beginner_display_order` を用意し、選びやすい順で表示しています。

### 選択順を「味わいの強さ」として重み付け集計

味わいタグは中間テーブル `drink_log_taste_tags` の `position` に**選択した順序を保持**しています。

店舗ごとの傾向表示では `DrinkLog#weighted_taste_tag_scores` により、
先に選ばれたタグほど高いスコアを与えて集計しているため、
単純な出現回数よりも「その店で強く感じられている味わい」が反映されます。

### 二重投稿の防止（冪等性キー）

ログ投稿フォームに `idempotency_key` を持たせ、
`user_id` との複合ユニークインデックスで**同じ送信が2件保存されないよう DB レベルで担保**しています。

Stimulus によるフロント側の二重送信防止と併用することで、
通信のリトライやブラウザバックからの再送信でもログが重複しません。

### 認可を Pundit のポリシーに集約

- 飲んだログの編集と画面上の削除は投稿者本人のみ。削除処理は管理者にも許可（`DrinkLogPolicy`。管理画面の導線は未実装）
- 管理機能は管理者ロールのみ（`AdminPolicy`）
- カフェは `draft` / `published` / `closed` のステータスを持ち、
  **非公開のカフェは URL を直接叩いても閲覧できない**ように制御

権限判定をコントローラに散らさず、ポリシーとリクエストスペックの両方で検証しています。

### N+1 対策とインデックス設計

- `DrinkLog.with_display_associations` で、一覧表示に必要な関連
  （ユーザー・カフェ・焙煎度タグ・味わいタグとその親）をまとめて事前読み込み
- 一覧の絞り込み条件に合わせた複合インデックス
  （`(cafe_id, status, created_at)` / `(user_id, status, drank_on)`）を用意

### 自宅で淹れた一杯も記録できる

`drink_logs.brewed_at_home` により、カフェに紐づかないログを許容しています。

`cafe_id` は `optional` にしたうえで、`brewed_at_home` が false のときだけカフェを必須にするバリデーションを置き、
「カフェのログ」と「自宅のログ」を1つのモデルで両立させました。

## 7. 開発環境のセットアップ

### 必要なもの

- Docker / Docker Compose

### 手順

```bash
git clone git@github.com:nonnopomu/coffee-compass.git
cd coffee-compass
cp .env.example .env
docker compose up
```

コンテナ起動後、別のターミナルでデータベースを準備します。

```bash
docker compose exec web bin/rails db:prepare
docker compose exec web bin/rails db:seed
```

http://localhost:3000 にアクセスすると起動を確認できます。

`db:seed` では、タグマスタ（焙煎度・味わい・店舗特徴）とカフェの初期データを投入します。
`ADMIN_EMAIL` と `ADMIN_PASSWORD` を `.env` に設定しておくと、管理者ユーザーも同時に作成されます。

### 環境変数

| 変数名 | 用途 | 開発時 |
|---|---|---|
| `GOOGLE_CLIENT_ID` | Google ログイン | 任意（未設定でもメール認証は動作） |
| `GOOGLE_CLIENT_SECRET` | Google ログイン | 任意 |
| `ADMIN_EMAIL` | seed で作成する管理者のメールアドレス | 任意（管理画面を試す場合に設定） |
| `ADMIN_PASSWORD` | seed で作成する管理者のパスワード | 任意 |
| `ADMIN_NAME` | seed で作成する管理者の表示名（既定値: 管理者） | 任意 |
| `RESEND_API_KEY` | メール送信 | 不要（本番のみ） |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_REGION` / `AWS_S3_BUCKET` | 画像ストレージ | 不要（本番のみ。開発はローカルディスク） |

開発環境から送信されたメールは http://localhost:3000/letter_opener で確認できます。

## 8. テスト・品質チェック

```bash
# テスト
docker compose exec web bundle exec rspec

# 静的解析（コードスタイル）
docker compose exec web bin/rubocop

# セキュリティスキャン
docker compose exec web bin/brakeman
```

上記3つは GitHub Actions により、Pull Request ごとに自動実行されます。

テストは以下の観点で書いています。

- モデルのバリデーション・関連（`spec/models`）
- 認可ポリシー（`spec/policies`）
- リクエストスペックでの権限制御・公開/非公開の出し分け・検索条件（`spec/requests`）
